# PREP-08. Поправка процесса: сценарии применения и планирование исследований

**English title:** Use-Case and Research Planning Process Amendment  
**Status:** DONE  
**Date:** 2026-09-20  
**Type:** process amendment  
**Applies to:** PREP-05 and related process/navigation/traceability documents

## 1. Назначение

PREP-08 устраняет процессный пробел, обнаруженный после завершения первоначальной подготовительной базы PREP-00…PREP-07 и до начала систематического цикла `RSCH`.

Поправка:

- вводит полноценный класс артефактов `USE`;
- определяет жизненный цикл и назначение `USE`;
- отделяет сценарии применения от вопросов, исследований и требований;
- добавляет `USE` в трассировку проекта;
- определяет роль `research-plan.md` без введения отдельного класса `PLAN-*`;
- уточняет роль GitHub Issues на текущей founder-led стадии;
- определяет правила языковых версий `USE`;
- задаёт навигацию по use cases;
- обновляет процесс PREP-05 без его переоткрытия.

[`PREP-05`](PREP-05-decision-process.md) остаётся `DONE`. PREP-08 является последующей целевой поправкой к процессу.

## 2. Причина поправки

PREP-05 определил классы:

- `Q`;
- `RSCH`;
- `REQ`;
- `DES`;
- `ADR`;
- `SPEC`.

Однако до начала систематических исследований остались два класса информации, не получившие формального места в процессе:

1. сценарии применения IMXO;
2. управленческий план исследований.

Сценарии применения нельзя корректно прятать в `Q`, `RSCH` или `REQ`:

- `Q` описывает неизвестность или вопрос;
- `RSCH` содержит исследование и доказательную работу;
- `REQ` фиксирует принятое проектное требование;
- `USE` должен описывать ситуацию применения, акторов/системы, проблему, ожидаемый результат и границы сценария.

План исследований также не является исследованием, доказательством, требованием или архитектурным решением.

## 3. GitHub Issues на текущей стадии

GitHub Issues остаются основным публичным каналом для:

- внешних предложений;
- существенных замечаний;
- вопросов от contributors;
- крупных изменений, для которых отдельная публичная точка обсуждения полезна;
- координации значимых Pull Requests;
- triage предложений, поступивших извне.

При этом Issue **не является обязательным промежуточным артефактом** для каждого внутреннего изменения проекта.

На текущей founder-led исследовательской стадии Project Lead может напрямую создавать или изменять `Q`, `USE`, исследовательский план, PREP amendments и другие процессные документы, если отдельный Issue не добавляет самостоятельной ценности.

Создавать Issue только для формального дублирования уже обсуждённого и документируемого решения не требуется.

Issue не является техническим решением и не заменяет `Q`, `USE`, `RSCH`, `REQ`, `DES`, `ADR` или `SPEC`.

## 4. Класс `USE`

`USE` — информативный проектный артефакт, описывающий сценарий применения IMXO.

Он отвечает прежде всего на вопросы:

- кто или какая система участвует;
- в каком контексте возникает задача;
- какая проблема или потребность существует;
- какой результат требуется от сценария;
- какие границы у сценария;
- какие известные ограничения есть у текущего workflow;
- почему сценарий может быть релевантен IMXO;
- какие открытые вопросы требует дальнейшего исследования.

`USE` не определяет архитектуру IMXO.

`USE` не является нормативным требованием.

`USE` не является доказательством необходимости функции.

`USE` не является обещанием включить функцию в конкретную версию стандарта.

## 5. Отличие `USE` от других классов

### USE vs Q

`USE` описывает ситуацию применения.

`Q` описывает неизвестность, которую требуется разрешить.

Пример:

```text
USE:
Пользователь сохраняет скриншот интерфейса.
Визуальный вид должен сохраниться, а текст должен оставаться программно доступным.

Q:
Как должна быть представлена связь текста с визуальными областями изображения?
```

Один `USE` может породить несколько `Q`.

Один `Q` может относиться к нескольким `USE`.

Исследование может обнаружить новый `USE`.

### USE vs RSCH

`USE` описывает контекст и ожидаемый результат.

`RSCH` проверяет факты, альтернативы, ограничения и гипотезы.

Наличие `USE` само по себе не подтверждает рыночную, техническую или регуляторную значимость сценария.

### USE vs REQ

`USE` не превращается автоматически в `REQ`.

Связь `USE → REQ` означает трассируемость мотивации и контекста, а не автоматическое происхождение нормативного требования.

Один `USE` может быть связан с несколькими `REQ`.

Один `REQ` может быть связан с несколькими `USE`, `Q` и `RSCH`.

### USE vs DES / ADR / SPEC

`USE` не выбирает реализацию.

`DES` сравнивает и проектирует варианты.

`ADR` фиксирует принятое архитектурное решение.

`SPEC` содержит нормативный результат.

## 6. Процесс является графом, а не конвейером

PREP-08 не вводит обязательную линейную последовательность.

Типичные связи могут выглядеть так:

```text
USE ↔ Q
 \    /
  RSCH
    ↓
   REQ
    ↓
   DES
    ↓
   ADR
    ↓
   SPEC
```

Однако допустимы и другие трассируемые пути, например:

```text
USE → REQ
Q → RSCH → REQ
USE → Q → RSCH
RSCH → новый USE
RSCH → новый Q
```

Не каждый артефакт обязан проходить через все классы.

## 7. Идентификаторы USE

`USE` получает постоянный глобальный идентификатор формата:

```text
USE-0001
USE-0002
USE-0003
...
```

Правила идентификаторов:

- последовательность глобальная для класса `USE`;
- ID не зависит от языка;
- ID не зависит от каталога или темы;
- ID не переиспользуется;
- при замене сценария новым старый ID сохраняется в истории;
- новый самостоятельный или superseding сценарий получает новый ID.

Первый реальный сценарий после PREP-08 получает идентификатор `USE-0001`.

PREP-08 сам не создаёт `USE-0001`.

## 8. Статус USE

`USE` имеет один из следующих статусов:

### DRAFT

Сценарий создаётся или существенно недоописан.

### REVIEW

Сценарий готов к содержательной проверке или находится в процессе review.

Переход через `REVIEW` не обязателен для каждой карточки. Допустим `DRAFT → COMPLETE`, если отдельная стадия review не добавляет ценности.

### COMPLETE

Сценарий достаточно полно описан для текущей проектной работы.

`COMPLETE` означает зрелость документа, а не решение поддерживать сценарий.

`COMPLETE` не является эквивалентом `ACCEPTED`.

### WITHDRAWN

Карточка прекращена без завершения, например если была создана ошибочно, оказалась ранним дубликатом, потеряла смысл до завершения или была признана нерелевантной до состояния `COMPLETE`.

`WITHDRAWN` не означает, что сценарий был заменён другим.

### SUPERSEDED

Сценарий заменён другой карточкой `USE`.

Старый документ сохраняется.

Старый `USE` должен указывать `Superseded by: USE-xxxx`.

Новый `USE` должен указывать `Supersedes: USE-xxxx`.

## 9. Disposition USE

Зрелость документа и решение о месте сценария в проекте являются разными характеристиками.

Поэтому `USE` имеет отдельное поле `Disposition`.

Допустимые значения:

### CANDIDATE

Сценарий рассматривается как возможный сценарий IMXO, но решение о целевом статусе ещё не принято.

### TARGET

Сценарий признан целевым для направления развития IMXO.

`TARGET` не означает, что каждая функция, упомянутая в сценарии, автоматически становится требованием или входит в v0.1.

### NON-TARGET

Сценарий описан, но сознательно не рассматривается как цель IMXO в текущей модели проекта.

`NON-TARGET` полезен в том числе для документирования границ формата и антисценариев.

### DEFERRED

Решение по целевому статусу сценария отложено.

Причина должна быть кратко указана в карточке.

## 10. Изменение завершённого USE

Редакционные изменения, не меняющие смысл сценария, могут вноситься без смены статуса:

```text
COMPLETE → COMPLETE
```

Содержательное изменение того же сценария должно вернуть карточку на review:

```text
COMPLETE → REVIEW → COMPLETE
```

Если существенно изменены основной actor/system, цель, контекст, проблема, границы или смысл ожидаемого результата и карточка фактически становится другим сценарием, старый `USE` должен быть `SUPERSEDED`, а новый сценарий получает новый ID.

История не переписывается задним числом.

## 11. Информативный характер USE

Все `USE` являются **Informative**.

Use-case success conditions описывают желаемый результат сценария, но не являются conformance requirements.

Например:

```text
Пользователь может получить программно доступный текст из сохранённого изображения.
```

может быть success condition сценария.

Это само по себе не создаёт нормативное требование вида `A conforming reader MUST ...`.

Нормативные требования появляются только в соответствующих `REQ` и `SPEC` артефактах.

## 12. Минимальное содержание USE

Карточка `USE` должна содержать достаточно информации, чтобы понять сценарий без скрытых предположений.

Основные поля:

- ID и название;
- Status;
- Disposition;
- Created / Updated;
- Actors / systems;
- Context;
- Problem / need;
- Goal;
- Trigger, если применимо;
- Scenario;
- In scope;
- Out of scope;
- Inputs, если применимо;
- Operational profile;
- Longevity and verification expectations;
- Expected outcome;
- Success conditions;
- Failure and representation-divergence impact;
- Adversarial / misuse incentives;
- Structured-data exposure and data minimization;
- Current workflow and known limitations;
- Assumptions / hypotheses;
- Relevance to IMXO;
- Cross-cutting considerations;
- Open questions;
- Related artifacts;
- Supersession, если применимо;
- History.

Для характеристик, перечисленных ниже, точные числа и окончательные ответы не требуются. Допустимы явные значения `unknown`, `to be researched`, `estimated`, `range`, `not applicable` или их однозначные эквиваленты.

### 12.1. Operational profile

Когда это релевантно, карточка описывает:

- frequency / event rate;
- typical volume;
- peak or burst characteristics;
- interactive or batch nature;
- число и типы producers и consumers;
- реалистичность ручной проверки;
- чувствительность к processing/storage overhead.

Глобальный масштаб рынка или adoption не должен смешиваться с operational characteristics конкретного сценария.

### 12.2. Longevity and verification expectations

Карточка различает:

- expected useful lifetime;
- expected retention period;
- требуемый горизонт проверки provenance / integrity;
- возможную потребность в offline или self-contained verification;
- допустимость зависимости от внешних сервисов.

Этот раздел фиксирует ожидания сценария, но не выбирает cryptographic, PKI или archival architecture.

### 12.3. Failure and representation-divergence impact

Карточка рассматривает последствия, если structured data неверны, устарели, повреждены или расходятся с visible representation. Когда релевантно, она указывает:

- кто или какая система использует неверные данные;
- может ли ошибка вызвать автоматическое действие;
- заметит ли человек расхождение;
- обратимы ли последствия и насколько существенен возможный ущерб;
- какие representations или layers могут расходиться.

Для такого расхождения не требуется наличие злоумышленника.

### 12.4. Adversarial / misuse incentives

Карточка рассматривает:

- есть ли сторона, получающая выгоду от ложных или несогласованных данных, и кто это;
- что именно ей выгодно подделать;
- какое representation или layer является целью;
- кого или какую систему предполагается ввести в заблуждение;
- какой downstream effect возможен.

До принятия отдельной модели субъективные классы уровня угрозы или риска не вводятся.

### 12.5. Structured-data exposure and data minimization

Карточка учитывает, что structured data могут усиливать утечку, поскольку становятся machine-readable, searchable, indexable, copyable, удобнее для AI/agent ingestion и массового извлечения. Когда релевантно, она рассматривает:

- какие sensitive data могут попасть в structured layer и были ли они видимы в pixels;
- могут ли structured data содержать информацию, которая визуально пользователю не показывалась;
- можно ли исключить sensitive data во время capture и может ли source application помочь исключить sensitive fields;
- можно ли безопасно удалить данные после capture;
- какие связанные representations должны измениться при redaction / sanitization;
- риски indexing / search и AI/agent ingestion.

Обязательно рассматривается класс риска, при котором скрытое визуально значение остаётся раскрытым в structured representation, например:

```text
visible representation:
Password: ••••••••

structured representation:
Password: real-secret-value
```

Этот раздел не выбирает конкретный механизм защиты.

### 12.6. Разделение сценариев

Если два внешне похожих сценария существенно различаются по operational profile, lifetime, verification horizon, failure impact, adversarial incentives или privacy / structured-data exposure и эти различия способны привести к существенно разным требованиям, предпочтительны отдельные карточки `USE`.

Например, `Interactive screenshot for a human user` и `Screenshot consumed by an autonomous AI agent` могут быть самостоятельными сценариями. Этот пример не создаёт соответствующие карточки.

Не все остальные подразделы обязаны содержать текст, если они объективно неприменимы.

Пустые формальные разделы не должны создаваться только ради шаблона.

## 13. Solution neutrality

`USE` должен по возможности описывать проблему и ожидаемый результат, не предопределяя техническую реализацию.

Плохо:

```text
IMXO должен иметь TEXT chunk с UTF-8 payload.
```

Хорошо:

```text
Текст, визуально присутствующий на скриншоте, должен иметь программно доступное представление, связанное с соответствующей визуальной областью.
```

Конкретный container, field layout, encoding, chunk type, API или другой mechanism должен появляться только в тех артефактах, где это действительно исследуется или проектируется.

## 14. Assumptions и неподтверждённые утверждения

`USE` может содержать рабочие гипотезы.

При этом следует различать:

- наблюдаемый факт;
- подтверждённое внешним источником утверждение;
- проектное предположение;
- гипотезу;
- ожидаемую ценность.

`USE` не должен выдавать предположение о рынке, regulatory interpretation, пользовательскую боль или adoption claim за установленный факт без соответствующего исследования.

## 15. Cross-cutting considerations

Вместо обязательного набора пустых разделов `Security / Privacy / Accessibility` используется общий раздел `Cross-cutting considerations`.

В нём, когда релевантно, могут рассматриваться:

- Accessibility;
- Security;
- Privacy;
- Trust;
- IPR;
- Interoperability;
- Preservation / archival concerns;
- другие поперечные факторы.

Отсутствие релевантного фактора не требует создания пустого подраздела.

## 16. Completion criteria

`USE` может перейти в `COMPLETE`, когда:

- понятен контекст;
- определены основные actors/systems;
- определена проблема или потребность;
- понятна цель сценария;
- определены основные границы;
- описан ожидаемый результат;
- существенные operational characteristics описаны или получили явный статус неизвестности либо неприменимости;
- существенные lifetime и verification expectations описаны или получили явный статус неизвестности либо неприменимости;
- существенные последствия failure и representation divergence описаны или получили явный статус неизвестности либо неприменимости;
- существенные adversarial / misuse incentives описаны или получили явный статус неизвестности либо неприменимости;
- существенные structured-data exposure и data-minimization характеристики описаны или получили явный статус неизвестности либо неприменимости;
- assumptions/hypotheses не выдаются за факты;
- перечислены существенные открытые вопросы;
- скрытое архитектурное решение не встроено в сценарий;
- существующие связанные артефакты указаны, если они есть;
- установлен `Disposition`.

Для `COMPLETE` не требуется предварительно исследовать все неизвестности. Они должны быть видимы как `unknown`, `to be researched`, `not applicable` или иной однозначный статус, а не скрыты в предположениях.

## 17. Языковой процесс USE

Новые существенные `USE` разрабатываются вначале на русском языке.

До состояния `COMPLETE` английская версия необязательна.

Английская версия может быть создана раньше, если она нужна для внешнего review, сотрудничества, обсуждения с англоязычным contributor или взаимодействия с внешней организацией.

При переходе русской карточки в `COMPLETE` английская зеркальная версия становится обязательной.

Если обе версии уже существуют, их смысл, ID, Status, Disposition и ссылки должны поддерживаться синхронно.

Технические идентификаторы не переводятся.

## 18. Хранение и навигация USE

Русские карточки хранятся в:

```text
docs/ru/use-cases/
```

Русский индекс:

```text
docs/ru/use-cases/README.md
```

Индекс содержит компактную таблицу `ID | Name | Status | Disposition` и ссылки на карточки.

Содержимое карточек в индекс не дублируется.

Английский каталог `docs/en/use-cases/` создаётся тогда, когда появляется первая английская карточка `USE`.

Пустой английский каталог заранее не создаётся.

## 19. README-навигация

Класс `USE` должен быть видим из основной документационной навигации.

После PREP-08 обновляются:

```text
README.md
README.ru.md
docs/ru/README.md
docs/en/README.md
```

Русские документы должны ссылаться на `docs/ru/use-cases/README.md`.

Английская навигация должна объяснять, что use cases являются Russian-first working artifacts и что English mirrors создаются по правилам PREP-08.

До появления `docs/en/use-cases/README.md` нельзя создавать broken link на несуществующий английский индекс.

После появления английского индекса навигация обновляется на него.

Если `USE` упоминается в `Q`, `RSCH`, `REQ`, `DES`, `ADR` или другом Markdown-документе и карточка уже существует, идентификатор следует делать кликабельной ссылкой, если это не ухудшает читаемость.

## 20. Трассировка

`USE` добавляется в IMXO Traceability Register.

Предпочтительная логическая форма реестра:

```text
Requirement | Use cases | Questions | Research | Design | Decision | Specification
```

Связи являются many-to-many.

Колонка `Use cases` не является обязательной для каждого `REQ`.

Требование может возникнуть из security research, interoperability constraints, внешнего стандарта, parser-safety requirement или другого технического основания без конкретного пользовательского `USE`.

Аналогично `USE` может существовать до появления связанных `REQ`.

В карточках `USE` используются нейтральные ссылки:

```text
Related questions
Related research
Related requirements
Related design
Related decisions
```

Формулировка `Derived requirements` не используется как обязательная, поскольку причинность может быть сложной и many-to-many.

## 21. Research plan

Отдельный класс `PLAN-*` не вводится.

План исследований является living project-management document:

```text
docs/ru/project/research-plan.md
```

Он управляет:

- порядком исследований;
- приоритетами;
- зависимостями;
- охватом;
- связью planned topics с `USE` и `Q`;
- состоянием исследовательской очереди.

План исследований не является доказательством, research result, `RSCH`, `REQ`, `DES`, `ADR`, нормативным источником или техническим основанием решения.

Нельзя использовать `Based on: research-plan.md` как техническое основание для требования или архитектурного решения.

## 22. Создание research plan

PREP-08 определяет роль `research-plan.md`, но сам не создаёт заполненный первоначальный план исследований.

Начальный план формируется после появления первых содержательных `USE` и с учётом уже существующих `Q`.

Логика:

```text
PREP-08
  ↓
initial USE set
  ↓
initial research-plan.md
  ↓
RSCH-0001...
```

Это позволяет строить порядок исследований от реальных сценариев и открытых вопросов, а не заранее придумывать последовательность без контекста.

## 23. RSCH identifiers в research plan

План исследований не резервирует номера `RSCH`.

До фактического создания исследовательского документа topic остаётся строкой плана без `RSCH-xxxx`.

Идентификатор присваивается только при создании реального `RSCH`.

Это предотвращает фиктивные исследования, зарезервированные, но никогда не созданные документы и бессмысленные пропуски ID из-за изменения очереди.

## 24. Изменение research plan

`research-plan.md` является одним living document.

Git history хранит изменения.

Не создаются `research-plan-v2.md`, `research-plan-final.md`, `research-plan-final2.md` и аналогичные версии.

Перестановка приоритетов, добавление зависимостей или изменение очереди не требуют отдельного GitHub Issue, если отдельное публичное обсуждение не добавляет ценности.

Если новая тема исследования отражает новый существенный неизвестный вопрос, при необходимости создаётся соответствующий `Q`.

## 25. Поправки к PREP-05

PREP-08 требует обновить PREP-05 по заголовкам и смыслу, не полагаясь только на номера разделов.

Необходимо:

1. добавить `USE` в перечень классов проектных артефактов;
2. определить назначение `USE`;
3. добавить идентификаторы `USE-0001...`;
4. добавить lifecycle `USE`;
5. добавить `Disposition`;
6. обновить модель трассировки;
7. обновить типичную диаграмму процесса, сохранив нелинейность;
8. определить, что Issue — публичный входной канал, а не обязательный предшественник каждого артефакта;
9. определить роль `research-plan.md`;
10. обновить шаблон Traceability Register;
11. сослаться на `USE` template и use-case index.

PREP-05 остаётся `DONE`.

История первоначального решения сохраняется.

## 26. Первоначальная PREP-база

После появления PREP-08 формулировка `PREP cycle complete` становится неточной.

В актуальных README/context документах следует использовать смысл:

> Initial PREP baseline (PREP-00…PREP-07) was completed. PREP-08 was added as a targeted process amendment before systematic research began.

По-русски:

> Первоначальная подготовительная база PREP-00…PREP-07 была завершена. PREP-08 добавлен как целевая процессная поправка до начала систематических исследований.

Это не переоткрывает PREP-00…PREP-07 и не меняет их статус.

## 27. Что PREP-08 сознательно не делает

PREP-08 не:

- создаёт `USE-0001`;
- создаёт заполненный initial research plan;
- запускает `RSCH`;
- создаёт `REQ`;
- выбирает container architecture;
- определяет logical object model;
- определяет physical file structure;
- принимает accessibility profile;
- принимает conformance profile;
- превращает adoption hypothesis в requirement;
- вводит отдельный класс `PLAN-*`;
- вводит обязательный GitHub Issue перед каждым внутренним артефактом.

## 28. Результат PREP-08

После PREP-08:

- `USE` является официальным классом проектных артефактов;
- его назначение отделено от `Q`, `RSCH` и `REQ`;
- определены ID, Status и Disposition;
- определены правила изменений и superseding;
- `USE` включён в трассировку;
- определены языковой workflow и навигация;
- определена роль `research-plan.md`;
- `PLAN-*` не вводится;
- Issues используются там, где дают реальную ценность;
- PREP-05 обновлён, но остаётся `DONE`;
- проект готов к созданию первых `USE`, а затем initial research plan и `RSCH`.

Следующий процессный шаг после публикации PREP-08 — создание первых реальных use-case cards начиная с `USE-0001`.
